1. What BioShell is and how it is deployed
It is an OpenStack VM image ("a ready-to-use cloud bioinformatics environment") built with Packer + Ansible on Ubuntu 24.04 (Noble) (README.md; build/openstack-bioshell.pkr.hcl). The Nectar base image is NeCTAR Ubuntu 24.04 LTS (Noble) amd64; the Nirin base is Ubuntu Noble Minimal 2026-01-30 (build/packer-vars/*.pkrvars.hcl). The image is named bioshell-v${image_version} (default 1.0.0). The build disk is 20 GB (volume_size).
It runs on ARDC Nectar and NCI Nirin (pages/about.md, pages/aup.md). The partners are Australian BioCommons, SIH, ARDC and NCI (index.md). It is not HPC: the guide contrasts it with Gadi and points batch users to ABLeS (pages/why-bioshell.md, pages/access.md).
The build runs three playbooks in order: build-bioshell.yml (roles common, singularity, nextflow, rstudio, cvmfs, shelley, globus_connect_personal, motd), then test-bioshell.yml (validate_* roles), then cleanup-bioshell.yml, which wipes the pip/uv/go caches, the apt lists, /tmp and the CVMFS cache.
All versions are pinned in build/ansible/vars/tool-versions.yml. A GitHub Action (.github/workflows/update-tool-versions.yml, cron 1 Jan and 1 Jul) runs check-versions.py, bumps the MINOR image_version and opens a PR. Updates happen twice a year (docs/MAINTENANCE.md). A v1.0.0 tag exists, seen via git ls-remote on AustralianBioCommons/BioShell, which appears to be the same repo: same HEAD, and the guide links issues there.
Users and sudo. Each approved project gets a dedicated VM (pages/aup.md "Service capacity"). The guide says users "have administrator access to install software" (pages/why-bioshell.md). The documented workflows assume sudo: sudo passwd, sudo rstudio-server start (pages/interactive.md) and sudo apt install htop (pages/flavours.md). The operations team also keeps admin access (pages/aup.md). The software layer is nonetheless designed for several users: shelley v0.3.0 made module builds shared (root-owned under /apps, built through a sudo -E re-exec; shelley/CHANGELOG.md, docs/explanation/build-design.md).
Training VMs are different. A provisioning script creates userNN accounts, with passwords derived from the username, and copies /etc/skel/ into each home. Developers prepare the image as tdevNN on dev VMs D1..., and the VM is then snapshotted (pages/training-development.md). Unverified: whether trainees have sudo, and whether a trainee VM has one user or many. The provisioning script is not in the repo; a manage directory was deleted on 2026-08-06 (commit 8780dcc).
2. How software is delivered now
CVMFS: only data.galaxyproject.org and singularity.galaxyproject.org are mounted (cvmfs_repositories, roles/cvmfs/tasks/main.yml). The CERN, EGI and OSG configs are disabled. The cache quota is CVMFS_QUOTA_LIMIT=4096 (MB). The proxy is DIRECT on Nectar and NCI proxies on Nirin (vars/nirin.yml), and CVMFS_USE_GEOAPI=yes. A var cvmfs_biocommons_url: http://bcws.test.aarnet.edu.au/cvmfs/@fqrn@ is defined but not used anywhere. A BioCommons dataset repo over CVMFS is described as future work (pages/training-development.md).
Containers: SingularityCE 4.5.0, not Apptainer. It is compiled from source with Go 1.26.4 into /opt/singularity/4.5.0, and LMOD_SYSTEM_DEFAULT_MODULES="singularity" in /etc/environment auto-loads it (roles/singularity).
shpc 0.1.33 is installed as an editable install in the venv /opt/shpc-env, with a launcher at /opt/shpc/bin/shpc. The Ansible role sets the central settings to $HOME/shpc/{modules,containers,wrappers,views}. shelley overrides these with /apps/shpc/settings.yml, passed as --settings-file, giving module_base /apps/shpc/modules and registry /apps/local (shelley/docs/reference/data-sources.md).
Lmod comes from apt. The default modulepaths are commented out, and only /apps/Modules/modulefiles and /opt/Modules/modulefiles are used (roles/common). Convention: software lives in /apps/<tool>/<ver>/bin (mostly symlinks to system binaries) with a Tcl modulefile at /apps/Modules/modulefiles/<tool>/<ver>. The singularity and shpc modulefiles are in /opt/Modules/modulefiles.
shelley is installed with uv tool install (uv at /opt/uv, tool env /opt/uv/tools, binary /usr/local/bin/shelley; roles/shelley). It indexes /cvmfs/singularity.galaxyproject.org/all: the cache has 122,520 entries across 13,187 tool names (shelley/data/galaxy_singularity_cache.json.gz, generated 2026-07-21), and search uses RSEC/bio.tools EDAM metadata. shelley build runs shpc install --keep-path, so the SIF stays on CVMFS, and symlinks the result to /apps/Modules/modulefiles/<tool>/<ver>.lua. When a version is missing from the upstream shpc-registry, it writes a local registry entry under /apps/local/ (v0.4.0) and generates aliases by diffing the container against base images with container-guts. shelley/data/guts_db/ adds miniconda manifests so that about 90 conda binaries are not exposed as aliases (docs/explanation/build-design.md).
Other installed software: Nextflow 26.04.6 (jar pre-fetched, Java 21) and nf-core 4.0.2 in a venv at /apps/nf-core/4.0.2 (roles/nextflow). Snakemake comes from apt (labelled 7.32.4). Ansible comes from apt. Globus Connect Personal 3.2.9 is under /apps/globusconnectpersonal. Spack is git-cloned unpinned (--depth=2) to /usr/local/spack and appended to PATH in /etc/environment. It has no modulefile and is not mentioned in the user guide (roles/common).
3. Current state of R and Python
R: r-base from Ubuntu Noble apt, with no CRAN/Posit apt repo, so R is 4.3.3, the Noble version. r_version: "4.3.3" is only a label. /apps/R/4.3.3/bin/R is a symlink to /usr/bin/R, and the R/4.3.3 modulefile just prepends that path; docs/Using_BioShell.md says the module is "for visibility" only. Build dependencies for R packages are installed (cmake, gdal, curl/xml2/fontconfig/harfbuzz/fribidi/udunits2/glpk/BLAS/LAPACK/OpenBLAS, tiff/jpeg/png/cairo; roles/common, commit e542aa6). No R packages are pre-installed: there is no BiocManager, renv, pak, IRkernel or Posit Package Manager config, and no Rprofile.site/Renviron.site changes. The auto-bump checks apt-cache madison r-base on an ubuntu-24.04 runner (check-versions.py). Inference: that check will effectively never move off 4.3.3, and even if the label changed, the apt install itself is unpinned.
RStudio Server 2026.06.0-242 is installed from the jammy .deb on Noble. Autostart is disabled; users run sudo rstudio-server start, and the server listens on port 8787 with PAM login using the Linux password (roles/rstudio). The modulefile reads the public IP from the metadata service at 169.254.169.254. It is the open-source build; there is no Posit Workbench.
Python: system python3 from Noble (inferred 3.12; no version is pinned anywhere), plus python3-pip and python3-venv. There is no conda, mamba or micromamba, and no pyenv. uv is installed system-wide but is used only for shelley. Its documentation explicitly cites PEP 668 ("externally managed") and the need for "conflicting python versions … in parallel" as reasons to avoid system pip (shelley/docs/explanation/install-design.md). Python venvs on the image: /opt/shpc-env and /apps/nf-core/4.0.2.
Jupyter: apt jupyter package. jupyter_version: "2026.07" is a timestamp, not an upstream version (check_jupyter in check-versions.py). The guide's own sample output shows classic Jupyter Notebook 6.4.12, started with jupyter notebook --ip=$IP on port 8888 with token auth (pages/interactive.md). There is no JupyterHub, no IRkernel, and no systemd service.
Package install guidance in the user guide: only pages/training-development.md covers it, and only for trainers. R users are told to run install.packages("ggplot2") and BiocManager::install("DESeq2"), which install to ~/R/x86_64-pc-linux-gnu-library/<ver>. Python users are told to run pip install --user <package> (to ~/.local/lib/python<ver>/site-packages), with kernels under ~/.local/share/jupyter/kernels/ and an example of "a conda environment" as a kernel. All of these are copied into /etc/skel with the warning "Seurat, Bioconductor suites can be several gigabytes". pages/tools.md says Shelley "currently only support[s] command-line tools and [is] working on extending this functionality out to R and Python packages". This is the only roadmap statement on the topic. The research-user pages give no package guidance at all.
CVMFS already holds containerised R and Python packages: 3,338 bioconductor-* names, 767 r-* (including r-base, r-seurat, r-tidyverse), 1,639 mulled-*, plus python, numpy, pandas, scanpy and anndata (counted from the shelley Galaxy cache).
4. Target users, training and workflows
Eligibility: Australian molecular life-science research and development projects. Allocations last 3 months and are renewable, with a default quota of 100 GB, up to 1 TB on request (pages/access.md). No sensitive or human-identifiable data is allowed, and nothing is backed up (pages/aup.md). The service is funded to 30 June 2028.
Sizing examples are R/Python-heavy: the "Moderate" tier (4-8 CPU, 32-64 GB) is for "interactive multi-step R or Python analysis", using scRNAvigator in RStudio as the example (pages/flavours.md).
Training is "the environment Australian BioCommons uses for all command-line-based training" (pages/access.md). The listed workshops include R-centred ones: scRNA-seq in R (Seurat, Harmony, SingleR; 2026, plus a QCIF rerun), Spatial omics (Bioconductor, 2025, plus a rerun) and Spatial sampler (Seurat). They also include RNA-seq (nf-core + RStudio, 2023), several Nextflow and nf-core workshops, and Linux intro (pages/community/training/*.md). Peter Mac reran a workshop "using a BioShell image saved in our workshop library".
Workflows: Nextflow pointed at CVMFS SIFs via container = 'file:///cvmfs/singularity.galaxyproject.org/all/...' or module = '<tool>/<ver>', with -profile singularity (pages/tutorials/nextflow-howto.md).
5. Storage and network
Root disk: 30 GB (/dev/vda2). The base image uses about 13-14 GB, leaving about 16 GB. That space covers home, /etc/skel, the CVMFS cache and any R or Python libraries (pages/training-development.md, pages/connecting.md).
Data volume: /mnt/data on /dev/vdb (example 100 GB) for working data (pages/connecting.md). The data volume is not created by the image build (operator-provisioned; how is unverified). Inference: user R/Python libraries in ~ currently land on the small root disk.
Network: outbound internet is assumed throughout: CVMFS over HTTP, get.nextflow.io, CRAN/Bioconductor/PyPI installs, and Globus relays. Inbound access needs security-group rules for ports 22, 8787 and 8888, and Jupyter and RStudio are served over plain HTTP (README.md).
6. Gaps and contradictions
JupyterLab vs Notebook. The guide says "JupyterLab" in many places (tools.md, interactive.md, connecting.md, access.md). The instructions and output are classic Notebook 6.4.12, and the repo installs apt jupyter.
R in Jupyter. "Python, R, and shell notebooks" (interactive.md) is not supported: no IRkernel is installed.
pip install --user will fail on Ubuntu 24.04 because of PEP 668, unless the user adds --break-system-packages. shelley's own docs acknowledge this restriction. Inference; not tested on an image.
BiocManager::install assumes BiocManager is present, and it is not pre-installed. R 4.3 also limits users to an old Bioconductor release (3.18). Inference: current Bioconductor needs a newer R.
"Conda environment" kernels are mentioned in the guide, but no conda is shipped.
The R and Jupyter modules are cosmetic. They point at the same single system install, so version switching is not possible. The r_version and jupyter_version auto-bumps cannot change what is actually installed.
Stale examples. pages/tutorials/shelley-howto.md shows R/4.3.3 … nextflow/25.10.4 rstudio/2023.12.1, while the repo pins RStudio 2026.06.0 and Nextflow 26.04.6. docs/Using_BioShell.md uses shelley versions STAR, which is not in shelley/docs/reference/cli.md (find, search, build, clean, interactive).
Spack is on PATH but has no modulefile, is not pinned and is not documented. docs/Using_BioShell.md lists it among the "modules".
Where modules live. The guide says home holds "installed modules" (connecting.md), but shelley now builds into the shared /apps tree (v0.3.0). The Ansible role still sets the shpc central config to $HOME/shpc; shelley overrides it, but direct shpc users would still build into their home.
Mixed upstream links. Docs link both AustralianBioCommons/BioShell and Sydney-Informatics-Hub/BioShell, and the shelley README links Sydney-Informatics-Hub/bioimage.
RStudio build mismatch. The RStudio jammy .deb runs on a Noble base.
Untracked R/Python work. No issue, template area or roadmap item for R/Python environments was found. The feature-request template areas are Shelly CLI, VM setup, Nextflow, Docs and Other. The shelley CHANGELOG references BioShell issue #22 (tools with no shpc registry). The open issue list could not be checked (see the note at the top).
7. Design implications (inferred)
The design must cover two user modes: a solo research VM where the user has sudo, and a snapshot-based training image with many accounts built from /etc/skel. It must also work within a root disk of about 16 GB free.
The existing conventions are an obvious place to plug in: /apps/<tool>/<ver> plus Lmod modulefiles, uv already present system-wide, SingularityCE and shpc for containerised r-*/bioconductor-*/python images on CVMFS, and the twice-yearly pinned-version bump workflow.
Any new R (rig/Posit binaries, P3M) or Python (uv-managed interpreters, micromamba) layer will need: modulefiles; RStudio pointed at the selected R (rsession-which-r / /etc/rstudio/rserver.conf); Jupyter kernels registered; library locations moved off the root disk or into shared site libraries; and guide updates for points 1-5 above.
