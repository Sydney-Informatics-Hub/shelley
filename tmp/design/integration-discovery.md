### What shpc needs from shelley (shpc 0.1.33 source on the VM)

| Fact | Evidence |
|---|---|
| With `--keep-path` and a local image, shpc uses the given path as-is and never reads the tag's `sha256:` value. The tag *key* must exist in the entry, or shpc exits "is not a known identifier" | `[code]` `/opt/shpc/singularity-hpc/shpc/main/modules/module.py:44-53`, `:99-109`; `main/modules/base.py:424-438` |
| Digests are used only when shpc pulls an image itself | `[code]` `main/container/singularity.py:243-254` |
| The upstream registry is resolved over HTTP (`requests.get` of the registry's web index). An install whose entry exists only upstream cannot succeed offline; an install from a local entry can (spike B) | `[code]` `main/registry/remote.py:164-186`; `[runtime]` spike B |

Consequence `[inferred]`: shelley's full-SIF hash (`cvmfs_builder.py:382`) costs a full read of the SIF through the 4 GB cache and buys nothing for the install.

## 3. Comparison: Galaxy vs EESSI

| Dimension | Galaxy Singularity (in production) | EESSI (work in progress, comparison only) |
|---|---|---|
| What is delivered | One SIF per `tool:tag` | A whole software stack: compat layer, CPU-optimised installs, Lmod modulefiles |
| Build step needed | **Yes**: `shpc install --keep-path`, harden, symlink, as root | **No**: expose an existing module tree (e.g. add to `MODULEPATH`) |
| How module files are provided | Generated by shpc into `/apps/shpc/modules`, symlinked by shelley | Shipped on the mount (EasyBuild-generated Lua) |
| Naming scheme | `tool:version--build`, lowercase Bioconda names | `Name/version-toolchain-tcversion[-suffix]`, e.g. `R/4.5.2-gfbf-2025b`; case-sensitive names |
| Architecture specificity | None in practice (amd64 images, amd64 VMs) | Per CPU target, chosen at initialisation (`x86_64/amd/zen2` here) |
| How to enumerate versions | List one directory (125k entries) or read the snapshot | Walk `modules/all/<Name>/` per EESSI version and CPU target (673 / 642 / 273 names) |
| Update cadence | Continuous, append-only, about 280 entries a week | Dated releases (2023.06, 2025.06, 2026.06) filled in over time; 2026.06 has R 4.6.1 but no Bioconductor bundle yet |
| Failure modes | Mount absent or slow (5–10 s timeouts, 1 retry); cache pressure from large SIFs; upstream shpc-registry unreachable (T6); stale snapshot (misses new tags) | Mount absent; module name conflicts (`conflict("R")` vs BioShell `R/4.3.3`); CPU target differs when a snapshot moves to other hardware `[inferred]` |

Bounded-context reading `[inferred]` (Evans): the two share only "a tool or package name a user can load". Galaxy's model is containers and registry entries that shelley builds; EESSI's is modules that already exist. That argues for two models behind one catalogue entry, not one shared model. This is a Phase 5 option, and not needed while EESSI is work in progress.

## 5. Decisions (Fred, 2026-10-07)

- **Q1:** single source of versions = the bundled snapshot for listing, a live check of the chosen SIF at build time, and a full live listing only when a requested tag is missing. Fred will raise the snapshot refresh cadence from monthly to **fortnightly**.
- **Q3:** when the network is unavailable, `build` **fails fast before writing anything**; it does not degrade. The message must tell the user what to do next, e.g. try again in a few seconds and check the network connection. (Fred's exact check command was cut off; a proposal is awaiting confirmation.)
- **Q2:** ordering spike done (`spikes/q2_results.md`). Conda's version ordering is right in 43 of 45 clear cases (build's rule 36, find's 8). 271 of the 331 disagreements are `mulled-*` hash-tagged containers, which have no version order. The rule itself awaits Fred's decision.
- **Q2 rule (decided):** conda's version ordering for named tools, with a leading `v` normalised away and non-version tags (`latest`, `broken`, …) never chosen as latest. The `pN` gap (2 tools) is accepted. For `mulled-*` containers, an explicit tag is required, and the error lists the available tags.
- **Q3 message (refined):** the check command is `curl -sI`, but its output is not beginner-friendly. Proposal for Phase 5: shelley runs the reachability check itself and reports in plain words which service it could not reach and why (no DNS, timeout, proxy refused). Raw command output is never shown to the user.
